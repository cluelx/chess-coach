# 复盘局面到高相似战术题：调研与实施建议

调研日期：2026-11-12。本文是代码审计与方案，不表示已实现或已测得准确率；未训练模型、未批量跑引擎。

## 结论

第一版建议采用 **结构化棋盘 + 战术关系图/变化序列匹配 + 引擎复核 + 明确拒荐**。先只支持少量容易严格验证的模式，如底线杀、闷杀、马双攻和绝对牵制得子。模型可以随后帮助扩大候选召回，但不要让向量分数或 LLM 判断直接决定“这题与你的失误高度相似”。

用户强调的重要棋子分布相似、战术思路相似，应当是两个必须同时满足的条件。仅同为“fork”、棋盘看起来很像，或者最佳着同为吃后，都不够。

## 1. 当前项目实际做了什么

- `src/app.py:275` 以知识点、学员档位和学员 ID 调 `sample_for_review()`；没有传入待匹配 FEN 或引擎变化。
- `src/puzzles.py:129` 抽取同知识点题目，再拆成做过/没做过。`pick()`（46 行起）按主题和等级筛选，并含随机抽样；题不够会放宽评级范围（82 行）。这属于**同知识点练习**，不是棋形相似检索。
- SQLite 只读检查：当前 34,747 道题、37 个入库主题。`scripts/fetch_puzzles.py` 只保留 wanted 集合中的标签，并有分段数量上限；当前库不是 Lichess 全量库，因此很可能没有某个局面的近邻。
- `src/db.py:17` 保存 FEN、走法、评级等，没有动态特征、关系图、引擎认证记录。导入脚本未存 `GameUrl`，后续数据溯源宜补存。
- `src/puzzles.py:32` 正确区分 `pre=moves[0]` 与 `solution=moves[1:]`。做索引时必须同样先应用第一步，再把得到的局面作为解题起点。直接拿 CSV FEN 做匹配会错一个半回合。此语义由 [Lichess 数据库说明](https://database.lichess.org/#puzzles)确认。

因此，应增加独立的 `find_similar(position, verified_tactic)`，保留原有 `sample_for_review()` 作为普通知识点练习。严格匹配失败时，不能用原随机抽题结果冒充“相似题”。

## 2. Fenformer、棋盘模型和程序匹配分别解决什么

| 路线 | 核验到的实际用途 | 本项目适用判断 |
|---|---|---|
| Fenformer | 实体棋盘照片到棋子摆放 FEN；DINOv2 编码器，64 个格子查询 | 有 PGN/FEN 时不需要。不能把图像识别准确率当成战术检索准确率 |
| Encoder-ChessLM | 8×8 棋盘、棋子位置、行棋方到 256 维表示；有相似题示例 | 可做候选召回实验；作者明确承认结构相似可对应截然不同评价，可能忽略动态因素 |
| 自训棋盘编码器 | 64 个离散格子 token 或 12×8×8 棋子平面，附状态；输出表示或配对评分 | 技术上可行，但需教学相似的正负配对数据；单纯预测最佳着或遮蔽棋子，不等于学会高精度类比 |
| 程序关系/序列匹配 | 明确表达攻击、保护、牵制、阻塞、逃跑格和将军/引离/得子序列 | 最适合第一版可解释、高精度、小覆盖范围；须引擎验证反击 |
| 混合方案 | 规则或向量召回，关系图和引擎筛选 | 建议长期路线；各阶段允许返回空结果 |

核验来源：[Fenformer 原始模型卡](https://huggingface.co/Eric-Xia/fenformer/blob/main/README.md)、[原作者代码](https://github.com/Ruichu-Xia/fenformer)、[Encoder-ChessLM](https://github.com/bluehood/Encoder-ChessLM)。本次 web 工具不能读取 Fenformer 页面，改用公开原始 README HTTP 请求实际读取。模型卡还提示其训练含非商业授权数据，要求按非商业权重对待；本方案无需接入该模型。

只输入 8×8 离散棋盘，不必称为 VLM。采用 Transformer 也不意味着需要视觉模型；对本网站已有精确状态而言，渲染图片再识别会增加不必要误差。**棋盘矩阵还不完整**：至少需要行棋方、易位权、吃过路兵状态；若涉及重复或五十步规则，还需要计数和棋谱历史。

## 3. 已有研究和实现值得借鉴什么

1. [Automatic Recognition of Similar Chess Motifs，Bizjak 与 Guid](https://ailab.si/matej/doc/Automatic_Recognition_of_Similar_Chess_Motifs.pdf)：直接研究相似战术检索，把静态位置关系与解题变化等动态特征结合，而非只看棋子落点。论文检索摘要已核验；本次未完整重现实验，不能借其结果宣称本项目精度。
2. [Retrieval of Similar Chess Positions，Ganguly 等](https://doras.dcu.ie/20378/)：把棋子位置、可达性与联系编码为可检索特征；有[实现仓库](https://github.com/CSSLab/chess-similarpos)。这是局面检索研究，不是“教学类比百分百正确”证据。
3. [Chess Query Language 官方文档](https://www.gadycosteff.com/cql/)：用明确棋子/走法序列查询棋谱，示例是 Bxh7+、Kxh7、Ng5+ 的希腊礼物模式，支持颜色变换及其它几何操作。很适合借鉴规则表达，但找到这串着法并不证明弃象正确或所有防守均失败。
4. [Similar Chess Puzzle Demo](https://github.com/ValentinKlamka/Similar-Chess-Puzzle-Demo) 的公开帮助文档确有相似题体验；检查前端可见其请求远端 API。本次没有核验到后端检索算法及质量测试，不能把演示页面当成成熟算法证据。

这些资料共同支持一个方向：**动态战术关系比单纯棋盘外观更重要**；目前没有核验到可以直接接入、即保证用户要求的“极高精度、不误荐”的现成模型。

## 4. 建议的高精度流水线

### 4.1 先明确在复盘中的哪个局面找题

- 玩家漏掉制胜手：查询玩家落子前局面，解法为引擎最佳着。
- 玩家失误让对方获得战术：查询玩家落子后局面，解题方是对手。
- 玩家实际走出了正确战术：查询落子前局面，解法为该着。

显示“你错过的机会”或“对手获得的机会”，不能只给 FEN 却默默交换教学视角。所有题统一归一为“解题方/防守方”，同时保留原颜色用于展示。

### 4.2 离线给题建立可验证签名

建议保存：`puzzle_id, start_fen, source_url, original_themes, solver_color, core_pieces, relation_graph, action_sequence, outcome, engine_version, limits, verification_status`。

- 核心棋子含进攻子、目标子、保护子、挡线子、国王与关键兵，不是机械取“发生过移动的子”。远处防守车可能决定杀棋能否成立。
- 图的节点是棋子角色与关键空格，边是攻击/合法防守/牵制/同线/阻隔/封锁逃跑格；保留关键相对坐标、线距离、边界与兵升变距离。
- 变化签名表示动作及因果，如“将军引王 → 马将军双攻王后 → 对王应将 → 吃后”，区别于没有将军的双攻。
- 同时记录最终目的：将杀、得后、净得子、逼和等。赢后但被杀，不能归入成功得子模式。
- 合法棋步必须用棋规库检查。`python-chess` 的攻击图与合法吃子不是同一个概念，被钉子也可能出现在攻击集合中；接口语义见[官方文档](https://python-chess.readthedocs.io/en/latest/core.html)。

### 4.3 候选召回与严格匹配分开

先用已验证主战术、结果类别、关键棋子类型、将军序列等建索引，缩小候选；未来可把棋盘 embedding 候选并入。这一步追求不漏候选，不直接展示。

严格层要求核心角色可一一对应，关键几何关系相符，动态顺序相符、局面的必要条件成立。第一版可只支持精确核心几何匹配，宁可没有结果。

不要允许任意旋转/镜像后直接判等价：兵走向、边线、升变、易位和格色限制会破坏等价。颜色交换与竖直翻转须一起正确变换完整状态；水平镜像宜限制到不涉及易位且规则成立的模式。所有变换后的结果仍需合法性与引擎复核，不能将 CQL 的搜索变换当作棋理等价证明。

### 4.4 最后用引擎验证机制

对原局面和候选各自运行一致配置的 Stockfish，比较主变化及关键防守分支；在已识别核心动作处约束搜索或复查替代防守。不能仅因为两个首选都“获胜”就认定教学机制一致。

验证包括：候选动作合法；最佳防守下教学结果仍成立；没有关键局面外棋子的反击；加大搜索预算后判断稳定。将杀优先于物质收益；存在将杀时，应匹配将杀的几何和步骤，而非推荐“可以吃车”。

有限深度引擎与有限 MultiPV 不是形式证明，MultiPV=3 也没有覆盖所有防守。对短将杀可实现有预算的完整合法应将树验证；其它情况应保存分析预算并保守拒荐。棋局历史影响和棋规则时保留历史，不只传裸 FEN。

### 4.5 展示和拒荐

建议每个转折点最多展示 0–2 个严格相似例子，这是产品上限建议而非实验结论。两盘并排、对应核心棋子同色标记、逐步播放两条变化，并明确“相同处”与“不同但不影响机制处”。

找不到就写“暂未找到足够相似的题”。另可单独显示“练习同一知识点”，但不能把它放在高相似栏目中。也不要因为题库小或用户等级限制而降低相似门槛；可以先发现确实相似的高难题，再告知难度偏高。

## 5. 阈值与验收：先测精确率，再决定上线

不建议直接规定“cosine > 0.95 就一定相似”。不同模型、主题、题库的分数不可直接比较；最高分也可能全是错误结果。

先由教练标注一批真实复盘查询与候选对，分别评核心布局、战术机制、教学可迁移性，并记录分歧。设置困难负例：同主题不同机制；仅一子差异造成反杀；同棋形不同走棋方；存在更快将杀；兵方向/易位权差异；图相似但关键线被挡住。

数据按原始棋局/近重复局面分组切分，镜像和微扰不能跨训练、校准、测试集泄漏。原始 `GameUrl` 的保存因此也很重要。

主指标应是“实际展示结果的精确率”、严重误荐率、各主题覆盖率、拒荐率、延时。Recall、nDCG 或平均相似度不能代替精确率。阈值在校准集按主题选择，在独立测试集冻结验证，并报告置信区间；达不到标准的主题关闭自动推荐。

可以把精确率 ≥99% 作为**拟定目标**，不是现有能力。即使独立测试 300 个展示结果零错误，二项模型下单侧 95% 错误率上界仍约 1%（`1 - 0.05^(1/300)`），并不证明永远不会错；按主题有效样本可能更少，重复题也不能算独立证据。

## 6. 实施顺序

1. 先把现有同主题推荐标识准确，并补原始来源、原始全主题与解题起始局面字段。
2. 建立人工审核的小型相似对/困难负例集，选 3–4 种短战术实现关系与序列匹配。
3. 增加 Stockfish 复核、空结果、证据可视化；只让通过评测的主题上线。
4. 需要更高覆盖时扩题库，并比较规则召回、ChessLM 召回、混合召回的 precision–coverage 曲线。
5. 只有现成表示确实成为瓶颈且有标注数据时，才训棋盘配对模型；优先学习“两个局面是否可用于同一教学模式”的对比/排序目标，再保留规则与引擎守门。

这条路线把 AI 用在候选生成和讲解组织，把“是否真相似”的判断约束在可检查的棋局事实与变化上，更符合用户宁缺毋滥的要求。
