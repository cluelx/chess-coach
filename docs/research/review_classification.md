# 复盘交互与战术标签调研（2026-11-12）

本轮只研究并保存复现证据，未修改业务功能。结论：不能用“局面存在某种棋形”直接推出“这一步错在没有利用该棋形”。先用引擎确认失误和可行反击，再给已验证变化标注主题；无法确定因果就只显示评价变化。

## 1. 已核验的现状

| 位置 | 现状与问题 |
|---|---|
| `web/js/app.js:801–805` | 复盘棋盘设为 `interactive: false`，没有用户试走变化。底层 `board.js:242–285` 已有合法走子、升变及撤销，可复用。 |
| `src/engine.py:175`；`src/app.py:304` | 已有内部 `best_move(fen)`，HTTP 层只有引擎信息查询，尚无任意变化局面的分析接口。 |
| `src/review.py:108–127` | 只要存在估算可赚子着、用户没有吃子，就可能报“漏掉免费子”；有牵制没走也会报错，未比较这些棋与实战棋的引擎质量。 |
| `src/motifs.py:54–89` | 吃子收益只搜索同一落点的最多三半回合交换。它没有涵盖中间将军、转移吃子、长组合与杀棋补偿，因此不是“强制净赚”的证明。 |
| `src/review.py:174–179` | `pre` 是走完实战棋后的拷贝，此时本来就轮到对方；再次设置相同 `turn` 后与 `board` 相同。因此“走前/走后对方叉子比较”实际上比较了同一局面，`allowed_fork` 条件不能正常生效。 |
| `src/review.py:473–487` | `_kp_guess` 先检测吃子并返回 k08，再检测将杀；吃子将杀被归成吃子。单纯“最佳着是吃子”也不能说明失误原因是漏吃免费子。 |
| `src/review.py:493–523` | 同一步有评价下降与规则标签，就采用高严重度规则解释；没有证明该标签解释了下降的原因。 |
| `src/app.py:283`；`web/js/app.js:1009` | 无匹配知识点时，服务端和前端都补“局面判断”。删除它要同步处理两端。 |
| `src/engine.py:148–171` | 虽然参数有 MultiPV，只返回第一条且 PV 截为四半回合；不足以检查较长战术。未返回深度、节点、bound、原始 UCI PV 等完整证据。 |
| `src/engine.py:129–152` | 非法局面或引擎异常输出 cp=0，可能被当作真实均势参与转折分析；应使用明确失败状态与空评价。 |

另一个质量问题：`review.py:448–470` 比较两个独立局面的有限深度分数，偶尔会产生“下完变好”的搜索波动；不应仅据此认定妙手。mate 分数也应保留独立类型，不把全部逻辑建立在折算成 10000 的厘兵差上。

## 2. 用户截图实测：确实会把杀棋误说成漏吃子

按截图重建的 FEN（不是完整原始棋谱，半回合计数为推定值）：

```text
3q4/1Q6/3N2rk/6p1/2p5/6P1/1bP3PP/r4RK1 w - - 0 33
```

本地现有 Stockfish、depth=18、MultiPV=3 的输出：

| 候选 | 白方评价 | 引擎主变化 |
|---|---|---|
| Nf5+ | M3 | Nf5+ Kh5 g4+ Kxg4 Qf3# |
| Nf7+ | M6 | Nf7+ Kh5 g4+ Kh4 g3+ Kh3 Qg2+ … |
| Rxa1 | -2.89 | Rxa1 Bd4+ Kh1 Qxd6 … |

对最优着 **Nf5+** 实际调用现有 `analyze_move`，仍输出 `missed_fork`（建议 Nf7+）、`missed_capture`（建议吃 b2 象）、`backrank`。这是函数级实测，不是浏览器整条复盘链路测试；网页转折点过滤可能使部分标签不显示，但这些 findings 仍可进入知识点汇总。

另外用一个明确标为人工构造的合法单元案例 `7k/7p/6KQ/8/8/8/8/8 w - - 0 1`，`Qxh7#` 确为将杀，`_kp_guess` 却返回 k08。

复跑：在项目目录执行 `python docs/research/reproduce_review_tags.py`。结果在 `review_tag_reproduction.json`。这些是指定引擎与搜索预算下的证据，不将单条 PV 当作穷尽全部防守的数学证明，也不据截图推断原棋谱隐藏状态。

## 3. 其他项目可借鉴什么

Lichess 官方源码目录将 [ornicar/lichess-puzzler](https://lichess.org/source) 列作生成、审核、分类题目的项目。其 [generator](https://github.com/ornicar/lichess-puzzler/blob/master/generator/generator.py) 比较最佳与次佳着、递归延长战术并安排对方防守；[tagger](https://github.com/ornicar/lichess-puzzler/blob/master/tagger/cook.py) 对解题变化中的节点检测主题，区分将杀目标、吃子、叉子等。它并非只用初始局面的静态几何形状打标签。值得借鉴其“先有经过搜索筛选的解题线，再分类”的分层结构。

但不能把 Lichess 标签当成无误真值：其仓库 [issue #17125](https://github.com/lichess-org/lila/issues/17125) 讨论过漏检相对牵制等限制。其规则主要面向已经筛选的战术题，不能直接搬到所有普通实战局面上并宣布“错过战术”。复制具体实现前还应核对仓库许可证；本建议只描述算法结构。

[python-chess 引擎接口](https://python-chess.readthedocs.io/en/latest/engine.html) 支持 MultiPV、指定 `root_moves`、完整历史、PV 和搜索信息，足以实现当前项目所需反事实分析。无需训练语言模型来决定棋是否成立。

[Lichess 的评价说明](https://lichess.org/page/accuracy) 指出同样厘兵损失在均势与大优局面含义不同，使用基于评价的胜率映射。对本项目，显示 `+0.1 → +0.5` 是评价分，不要叫真实胜率；筛选转折点可同时考虑 WDL 期望变化，且区分映射模型与用户个人胜率。

## 4. 建议的保守分类管线

以下是本项目建议，不声称上游完全如此实现。

1. **统一局面与视角。** 传入初始 FEN、到该节点的 UCI 历史、当前着；验证合法性，固定同一方视角。保留将杀与普通分数的区别。引擎失败、超时、分数 bound 或未收敛时不强行解释。
2. **先确认是否真的值得批评。** 对同一根局面搜索最优着、实战着及规则提出的候选（用 `root_moves` 分别验证）。实战着与最佳着基本等价时不报“错过叉子/牵制”；保留杀棋的不同路线也不因漏掉某一棋形就判错。杀棋步数变长可作为效率说明，但不能自动视为重大错误。
3. **再确定主要目标。** 首先区分错失强制杀、允许对手强制杀、丧失可守和局、损失子力等。将杀目标优先；副主题只说明完成目标的机制。用户案例应强调杀棋，不能被吃子提示抢占。
4. **沿验证过的变化识别机制。** 叉子需检验对方最强反击及解围，牵制需证明它限制了关键防守/使具体收益成立；底线杀需有实际杀棋变化，不能仅凭王在底排和对方有重子。同格交换估值仅用于便宜筛选。
5. **反事实核验。** 对“应吃此子”的候选强制落子后搜索，若被杀/局面更差/不如实战着，撤销建议。对“送子”须检查弃子补偿、长将、杀棋。`is_pinned` 只检测绝对牵制，不足以覆盖相对牵制。
6. **不确定就弃权。** 只显示评价变化与可点击最佳变化，允许没有主题、没有相似题；不要为了凑三个转折点或固定推荐数填入低置信标签。

可先定义 `evidence={root_fen, history, played_uci, proposed_uci, score_before, score_played, score_proposed, pv_uci, engine_version, nodes, depth, validated_motif}`。LLM 仅把这份已验证证据改写成可读文本，不能增加没有证据的“必然”“唯一”“白吃”。

阈值不应拍脑袋定成某个 confidence=0.95。先建立人工审核集，涵盖杀棋优先、弃子、反将、相对牵制、多等价好棋、残局、静态假叉子等；分别度量每类标签精确率与拒绝率。严选阈值，记录审核样本量与置信区间；“在少量样本上零误报”不是保证绝不误报。

## 5. 变化试走界面与 API

主线数据保持只读；变化节点包含 `parentId, moveUci, fen, rootMainlinePly`。用户从任意主线节点试走后进入变化模式，可后退、继续试走，按“让对手走引擎最佳着”分析**当前变化盘面**并执行一手；另设“仅显示建议”与“回到主线”。回主线恢复进入变化前节点，而不是跳到棋局起点。切换节点后丢弃过期请求结果。

推荐新增 `POST /api/analysis/position`，请求包含初始局面和历史着法、预算及请求 ID；响应包含当前局面 ID、最佳着、评分、完整主变化和搜索状态。FEN 不能独自恢复重复局面历史，涉及三次重复时需要历史；五十步计数也要保留。终局返回终局状态，不能继续走子。后端已有锁能串行保护单引擎，但多人用时需有任务队列、取消、预算上限，避免拖动棋盘堆积分析。

## 6. 本版落地顺序

第一步：隐藏“局面判断”空标签和重复评价说明，保留 `+0.1 → +0.5`；停止把未经因果核验的规则结果纳入用户弱点记忆。第二步：加入变化试走、当前盘面引擎响应与回主线。第三步：以上述截图实测为回归案例，改成引擎验证后再分类；先开放少量高把握主题。第四步：只用通过验证的战术证据对接高相似度题库检索。
