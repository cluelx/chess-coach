# 临时复盘实验室

## 静态特征可视化

在“转折点”列表点击某手旁的“显示”，即可在同一页查看该局面的双方静态特征；点击逐回合概念也可跳到对应变化。当前实现21项，8、14、17、18、23、24、25、28、30明确标记为“尚未可视化”，不调用它们的候选走法计算，也不以空列表代替未实现状态。旧的逐条件观察模块保留为历史调试工具，当前前端不再加载。

蓝圈表示白方项目，橙框表示黑方项目；这是项目所属视角，不一定是目标棋子的颜色。例如白方施压的黑兵属于白方项目。可选择双方、单方及标记类别（通路兵、叠兵、弱格等）；点击一个项目显示对应坐标、原始攻防关系和计分依据。“标记全部目标”恢复当前筛选范围，“同时显示攻防关系”显示其中的关系。第15条默认展示双方对已占据格的攻防图。

所有特征采用固定类型、坐标、关系字段与固定格式文本；排序与ID稳定。页面的“固定格式返回信息”和“原始返回JSON”可展开检查，控制台也打印完整返回对象。JSON可切换当前概念或全部30项状态。测试记录与导出保留所选概念、局面、类别和项目。

特征清单是双方完整静态诊断，包括原规则因子力等条件提前退出时的诊断数据。`matched`由原规则布尔入口计算；`counted_in_feature_score`仅指是否计入该项静态特征分，不代表所有最终判定条件都通过。第3条达到原计分停止条件后的其他弱格、第22条未被选为最高分色格组的候选等仍返回，但注明不计分。背景/正常项目可额外展开；显式选择某类别会显示该类别完整清单。

第11条攻防关系排除王；第13、27条的活动范围为原规则估计，不是合法安全走法。第27条保留原计分使用的0、1、至少2，同时提供完整估计落点。子力表、限制条件和原布尔判定均不更改，已有Stockfish预计算无需重算。

接口：`POST /api/static-features`，请求 `{ "fen": "完整FEN" }`。实现：`src/review_features.py`。原库仍严格返回bool，详情入口复用原帮助函数并提取固定坐标证据。

验证：`python scripts/check_review_features.py`，覆盖原谱全部局面、三个固定种子的随机合法对局片段以及吃过路兵、升变、钉住、叠兵局面；检查双方原规则结果、坐标关系、静态分数与稳定输出顺序。

在 chess-coach 根目录运行：

```powershell
python scripts/review_lab.py --port 8770 --compute
```

打开 <http://127.0.0.1:8770/>。仅启动查表服务可省略 `--compute`，页面也能启动或暂停预计算。关闭页面不影响计算；停止服务后，下次运行上述命令可断点续算。请勿同时启动多个计算服务。

## 数据范围

- 从正式库以只读方式读取最新一份 `review_detail`，固定成独立快照。此次是 #28、70个半回合。原始PGN和已有复盘分析不改动。
- 每个实战局面分别用深度10、12、16、19计算该深度的推荐着，并与实战着比较。两者相同时共用一份变化。
- 每条变化最多12回合，即24个半回合，包含比较的首着。依照现行 `board.is_game_over()` 判定终局后提前停止，包括将杀、逼和、子力不足、五次重复及75步自动和棋；不自动申领三次重复或50步和棋。没有把未终局的短PV当成完整12回合。
- 方案包含双方最优主线、现行3×2、旧版8分支和扩展5×3。旧8分支严格按备份实现：对手首次应手的MultiPV8，再把SinglePV首选应手放到第一位，去重后取前8；此后双方逐手最优。3×2和5×3分别在对手前两次应手时展开；后续双方逐手最优。这些是候选采样树，不是全部合法走法的穷举。
- 优先计算后半盘转折点，再计算其他全部局面。四个深度各用一个worker、一个Stockfish，Threads=1、Hash=96MB。完成280个局面×深度后worker自行结束。

## 逐手重新搜索保证

`Calculator.line()` 每到一个新局面调用一次独立的SinglePV搜索，仅使用当次搜索返回的第一着。固定的对手分支着由该局面的MultiPV候选搜索提供，我方应手始终独立SinglePV。完整起始FEN和走棋历史传给每次UCI `position`，避免丢失重复局面信息。

每次未命中的查询发送 `ucinewgame`、`isready`，使用 `go depth N`，没有时间或节点上限。搜索失败不写成功缓存。若引擎在证明将杀后提前结束，记录真实深度及mate分数；页面原始数据可以核查。缓存键包含引擎文件哈希、搜索实现版本、深度、MultiPV数和完整历史。重复读取同一查询不会再次运行引擎。

缓存里保存每次查询的完整历史、首选/候选着、实际深度、节点数、墙钟耗时、引擎耗时以及score边界标志。页面“原始数据”支持审计；也可运行：

```powershell
python scripts/check_review_lab.py
```

审计会重放保存的所有变化，逐手验证合法性、SAN、FEN、完整历史和搜索记录对应关系，并验证非候选分支着都来自该局面SinglePV的第一着。它不把现有PV后面的着法当作独立查询。

## 怎样测

1. 选择转折点和深度，切换3×2、旧8分支、5×3或仅主线。
2. 改“读取回合数”，可直接截取已保存的12回合；不启动新搜索。成本表只统计生成当前截取长度所需的搜索，并包含方案所需的主线搜索。
3. 改概念候选起点上限和连续验证回合数。“再持续3回合”表示同一概念从起点起连续4回合为真。读取窗口不足的概念标为待验证，不当成不成立。默认起点上限9，使12回合可以完成后续3回合验证；现行代码上限7也可以选择。
4. 表中显示全部30种概念的原始证据、推荐/实战分支命中数、主线差异和未确认数量。可以选择筛选策略或手动勾选概念。将杀/净得子与概念同时展示；“旧优先级”用于实验性演示提前筛选内容的影响，不是对生产接口返回结果的逐字段复刻。
5. 点击变化的任意一手，在棋盘回放；展开每回合的概念证据。对手视角单独查看。负面结论只取双方最优样本主线的差异。
6. 保存人工记录和勾选，或导出当前局面的四深度缓存、规则和预览为JSON。保存到独立测试库，不回写正式复盘。

全部概念都评估在每个完整回合结束的局面，双方视角各一份，采用现有BinProp库的同一规则源码。为减少重复编译，可信的本地规则在计算worker中各编译一次，不更改规则。概念的布尔证据与引擎评价不同，某条采样最优主线中的成立也不等于对所有合法应对的强制证明。

## 耗时口径

表中“冷搜索合计”为生成该方案所需的独立查询去重后的墙钟耗时之和，不是网页查表耗时，也不是线上请求的实测响应时间。四worker并行时存在CPU竞争。节点数是查询工作量的参考；MultiPV中的nodes是累计数，每次查询只计最大值，避免按候选数重复相加。主线、旧8和3×2的MultiPV配置可能给出不同首选，这属于独立搜索的真实结果，不强行替换。

用于正式参数决策时，需要覆盖早、中、残局并比较共同完成的局面；单个战术局面的耗时不能直接推到整盘。这里保留所有数据，暂不据少量样本确定生产默认值。

文件位于 `data/review-lab/cache.sqlite3`，包含games、searches、results、progress、settings、notes表。它们可独立备份。库和引擎版本改变后重启服务会生成新的快照标识；已有数据不会伪装成新版本结果。临时页和启动脚本没有修改正式复盘的搜索或表述逻辑。
